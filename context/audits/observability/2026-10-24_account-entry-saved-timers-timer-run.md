# Audyt obserwowalności — account-entry, saved-timers, timer-run (2026-10-24)

## 1. TL;DR

- **Wyniki `{ error }` z Supabase są traktowane jak wyjątki.** auth-js nie rzuca (`throwOnError` domyślnie `false`), a kod czyta tylko `data` albo nic. Dlatego `try/catch` łapią wyłącznie bugi, a prawdziwe awarie nigdy nie docierają do `wrapRequestHandler`.
- **Najważniejsza konsekwencja:** awaria Supabase Auth (outage, 5xx, zły klucz) wygląda jak masowe wylogowanie. Każda chroniona strona przekierowuje na `/auth/signin`, API odpowiada 401, a w Sentry i w logach nie ma nic (`src/middleware.ts:38-41`). Tak samo awaria wysyłki magic linka kończy się 200 „link wysłany” i ciszą (`src/lib/email-auth.ts:173-184`).
- **„Zneutralizuj = wyrzuć”.** Wszystkie 40 `catch` w `src/` jest bez bindingu. Odpowiedź dla użytkownika jest neutralna (słusznie), ale błąd znika razem z nią. Nie ma wspólnego helpera „zaraportuj, potem zneutralizuj”.
- **Granica przechwytywania opiera się wyłącznie na `throw`.** Sentry nie patrzy na status odpowiedzi, przeglądarka nie ma żadnego `captureException`, a brakuje też `ErrorBoundary`. Awaria audio, Wake Lock, fetch w kontrolerach CRUD i błędy SSR po pierwszym bajcie streamu dają stan UI albo obcięte 200, bez zdarzenia.
- **Jedyny logger zapisuje sam kod błędu.** Każdy log to `"drill save failed <code>"` (też dla odczytu i usuwania), bez stacka, statusu i operacji. Awaria sieci daje pusty kod.
- **Domyślne ustawienia SDK.** Body żądań POST (email, `token_hash`, nazwa timera) i IP trafiają do zdarzeń. Brakuje `environment` i `setUser(id)`, a release klienta i serwera się różnią.

## 2. Model przechwytywania

- **Środowisko uruchomieniowe:** Astro 7.3 SSR na Cloudflare Workers (`@astrojs/cloudflare` 14.3). Odpowiedzi HTML są streamowane. Wyspy React 19. Nie ma pracy w tle po stronie serwera (`waitUntil`, cron, kolejki).
- **Serwer:** `@sentry/cloudflare` inicjalizowany per żądanie przez `wrapRequestHandler` w middleware (`src/middleware.ts:29-55`). Konfiguracja:
    - DSN z var `PUBLIC_SENTRY_DSN` (`wrangler.jsonc:8`), release `CF_VERSION_METADATA.id` (`src/middleware.ts:18`);
    - `captureConsoleIntegration(warn, error)` (`:26`), działa tylko gdy klient jest aktywny w scope żądania;
    - brak `environment`, `beforeSend` i `dataCollection`.
- **Wyjątki z ramek stron i endpointów** wychodzą z `next()` i są przechwytywane jako `handled:false` (`@sentry/cloudflare/.../wrapRequestHandlerWithInit.js`). Astro renderuje 500 dopiero po middleware (`astro/dist/core/routing/handler.js:101`). Sentry nie przechwytuje niczego na podstawie statusu, więc zwrócone 5xx, 4xx i redirecty są dla niego niewidoczne.
- **Błędy po pierwszym bajcie streamu HTML** (Layout, AppTopBar, komponenty zagnieżdżone, SSR wysp) trafiają do `controller.error(e)` (`astro/dist/runtime/server/render/astro/render.js:72`) i dają obcięte 200. Sentry klasyfikuje `text/html` jako odpowiedź niestreamowaną i kończy span przed renderem body. _Wyłącznie statycznie._
- **Logi samego Astro** (`console.error` przy błędzie renderowania) powstają po wyjściu z kontekstu ALS, więc `captureConsole` je odrzuca (`@sentry/core/.../captureconsole.js:22`). Trafiają tylko do logów Workers.
- **Flush:** `cfContext` istnieje (`@astrojs/cloudflare/dist/utils/cf-helpers.js:25`), a `flushAndDispose` jest planowany przez `waitUntil` na każdej ścieżce. Działa.
- **Klient:** `@sentry/astro` (`sentry.client.config.ts:3-6`) z DSN i `tracesSampleRate: 0.1`. Domyślne integracje (onerror, onunhandledrejection) są wstrzykiwane na każdej stronie Astro (`injectScript("page")`). W kliencie nie ma `captureConsole`, wywołań `captureException`, `ErrorBoundary`, `setContext` ani `setTag`. Source mapy wysyłane w CI (`astro.config.mjs:21-27`) i dopasowywane po debug ID.
- **Logowanie:** jedno wywołanie `console.error("drill save failed", code)` w `src/lib/services/drill-configurations.ts:226-229`. `captureConsole` robi z niego zdarzenie typu message bez stacka.
- **Czyszczenie danych:**
    - Domyślnie `httpServerIntegration` dołącza do 10 KB body każdego POST i PUT (`@sentry/cloudflare/.../baseSdk.js:25`, `integrations/httpServer.js:18`), a `userInfo: true` dodaje IP (`@sentry/core/.../resolveDataCollectionOptions.js:2-5`).
    - Ciasteczka `sb-*`, nagłówek `authorization` i `token_hash` w URL są filtrowane.
- **Tożsamość wdrożenia:** release serwera to UUID wersji Cloudflare, release klienta to SHA wstrzyknięte przez plugin bundlera. `environment` nie jest ustawione, więc SDK przyjmuje domyślnie `production`. Lokalny `.env` zawiera produkcyjny `PUBLIC_SENTRY_DSN`, więc lokalne buildy klienta wysyłają do produkcji. `.dev.vars` (serwer) i CI mają pusty DSN.

**Założenia (poza repozytorium, nie ustalenia), niepotwierdzone:**

- Zbieranie Workers Logs jest włączone (`observability.enabled` w repo), a Logpush i alerty są skonfigurowane poza repo.
- W Sentry istnieją reguły alertów dla nowych issue i ewentualne server-side data scrubbing, które może maskować emaile w `request.data`.
- `vars.PUBLIC_SENTRY_DSN` i `secrets.SENTRY_AUTH_TOKEN` istnieją w środowisku GitHub `production`.
- Stacki serwera symbolikują się po debug ID, czyli wrangler nie bundluje Workera ponownie.

## 4. Systemowe przyczyny źródłowe

1. **Wynik `{ data, error }` z Supabase jest traktowany jak wyjątek, a „brak użytkownika” znaczy dwie rzeczy naraz.**
    - Gdzie: `src/middleware.ts:38-41`, `src/lib/email-auth.ts:174-184`, `:201-211`, `src/pages/api/auth/signout.ts:6-9`. auth-js zwraca błędy, łącznie z `AuthRetryableFetchError` przy braku sieci (`@supabase/auth-js` `GoTrueClient.js`, `throwOnError=false`).
    - Ten sam mechanizm: `createClient` zwraca `null` bez logu (`src/lib/supabase.ts:7-10`), a `readFailure` zamienia bazodanowe 401 na `sign_in` bez logu (`src/lib/services/drill-configurations.ts:511-515`, `:568`, `:578`). Ścieżki „wylogowany” i „auth zepsuty” są nie do odróżnienia.
    - Wyjaśnia: A1–A5, S1.
2. **Neutralizacja przez wyrzucenie błędu.**
    - Gdzie: 40 `catch {}` bez bindingu, m.in. `email-auth.ts:182`, `drill-configurations.ts:265`, `:400`, `:449`, `:523`, `:544`, `drill-create-controller.ts:109`, `:208`, `drill-delete-controller.ts:290`, `:331`, `drill-audio.ts:72-78`, `drill-run.ts:289-293`, `drill-wake-lock.ts:89-93`, `src/pages/auth/callback.astro:77`.
    - Skąd: wymóg odpowiedzi neutralnej wobec konta i łagodnej degradacji (FR-002) jest słuszny, ale brak wspólnego portu „report-then-neutralise” sprawia, że neutralizacja i usunięcie dowodu dzieją się w jednym kroku.
    - Wyjaśnia: A2, A3, A6, A7, S2, S4, R1–R4, R7, R11, R13–R15.
3. **Granica przechwytywania tylko po `throw`, bez sygnału statusu i bez instrumentacji klienta.**
    - Gdzie: `wrapRequestHandler` przechwytuje tylko wyjątki z `next()`. Serwisy mapują awarie na odpowiedzi 4xx/5xx/200 (`src/pages/timers.astro:36`, bez `status = 503`). Błędy streamu omijają tę ścieżkę (`render.js:72`). W kodzie klienta nie ma ani jednego wywołania Sentry ani `ErrorBoundary`.
    - Wyjaśnia: P2, S7, S2, R5, R6, R9, R12.
4. **Logowanie samym kodem przez `captureConsole`.**
    - Gdzie: `drill-configurations.ts:223-229`. Komentarz chroni nazwę timera, ale przy okazji wycina status HTTP, `hint`, przyczynę sieciową (`code: ""`, `status: 0`) i obiekt błędu. Jedna etykieta „save” obejmuje list, find, update i delete. Nigdzie nie ma `setUser` ani tagów operacji.
    - Wyjaśnia: S3–S6, P6, R10.
5. **Domyślne ustawienia SDK przyjęte bez zmian dla prywatności i tożsamości.**
    - Gdzie: `src/middleware.ts:15-27` i `sentry.client.config.ts:3-6`. Body i IP są zbierane w nadmiarze. Brakuje `environment`, wspólnego release i `beforeSend`.
    - Wyjaśnia: P3, P4.

## 6. Zalecana kolejność poprawek

1. **Klasyfikacja błędów auth w jednym helperze serwerowym** (`reportAuthError(error, step)`).
    - Zamyka: A1, A2, A3, A5, częściowo A4.
    - Zasady: `AuthSessionMissingError`, `otp_expired`/`invalid` i 429 nie są błędami (najwyżej metryka). Raportowane są 5xx, `AuthRetryableFetchError` i błędy konfiguracji, ze statusem i kodem, bez emaila.
    - W middleware błąd retryable daje 503 zamiast „gościa”.
    - Najpierw nieprzechodzący test w `src/lib/*.test.ts` dla `getUser → { error }`.
2. **Ograniczenie danych zbieranych przez SDK** (P1). Małe i niezależne zmiany, które warto zrobić przed dodaniem kolejnych zdarzeń z body.
3. **Wspólny port „report then neutralise”** (serwer: `captureException` z tagiem `op`; klient: cienki wrapper na `@sentry/astro`).
    - Zastępuje `catch {}` w serwisie (S4), kontrolerach CRUD (S2), callbacku i SignInForm (A6, A7) oraz w audio, resume i Wake Lock (R1, R4, R7, R11, R13).
    - Musi rozróżniać oczekiwane `DOMException` (`NotAllowedError`, `AbortError`) od bugów, żeby nie zalać trackera.
4. **Logger z obiektem błędu i operacją** (S3, S6) + mapowanie sieci i gateway na 503 (S5) + `status = 503` na `/timers` (S7). Zachować zakaz logowania payloadu i `details` dla 23505.
5. **Kontekst:** `setUser({ id })`, tagi kroków, `setContext("drill")` (P4, R10), plus wspólny release i environment (P3).
6. **Bezpieczeństwo biegu:** zawężenie `catch` w `drill-run.ts` (R3, ryzyko rekursji), `ErrorBoundary` (R5), stan błędu dla `begin` i resume (R4, R6), raport dryfu (R9).
7. **Sygnały zero-row** dla update i delete (S8, S9) oraz pozostałe drobne poprawki.
8. **Sonda dla P2** (błąd SSR po pierwszym bajcie), zanim zaczniesz projektować poprawkę.
